# 0.7.1 — Hermes Skill-Activity View in the Traces Tab

> Format: Keep a Changelog (https://keepachangelog.com/). Semver bump:
> 0.7.0 → 0.7.1 — additive features only; backward-compatible schema
> migration; no contract changes to existing endpoints.

The Traces tab used to be a flat list of Hermes/Ollama request-response
bodies with one substring filter. From an operator's seat — "what is
Hermes doing for my SLM-Forge experiment right now?" — that view was
too low-level: you couldn't answer "which skill fired during this run?",
"did this skill regress only after its prompt changed?", or "did the
skill file change since the last invocation?" without scraping logs.

This release turns that page into a per-skill activity view with
honest skill-change detection.

> **Mental-model note (important).** Hermes does *not* auto-write its
> own skill files at runtime. Skills live as committed markdown under
> `.hermes-skills/`. What this release adds is **passive content
> hashing**: every Hermes call hashes the skill markdown at load time
> and persists the hash on the trace row. When that hash differs from
> the previous trace for the same skill, the UI surfaces a "skill
> content changed since last call" badge. This catches *any* change
> path — git pull, manual edit, or a hypothetical future Hermes
> auto-write — without inventing a fake "Hermes wrote this" signal.

## Added

- **Per-skill activity panel.** The Traces tab now shows a left-side
  rollup (`GET /api/v1/hermes/traces/skills/summary`): one row per
  skill with calls, error %, avg + p95 latency, current hash
  (truncated 16-char sha256), first-seen, last-seen, and a "changed
  N×" badge counting hash transitions. Click a row to filter the
  middle list to that skill.
- **Skill-change detection.** Every Hermes call now records
  `skill_sha256` (first 16 hex chars of sha256 of the skill markdown
  at load time) and `skill_mtime` (filesystem mtime, UTC). When this
  row's hash differs from the previous trace for the same
  `skill_name`, the API computes `skill_changed: true` and the UI
  shows a purple `✎ skill changed` badge in the list + a detail-pane
  callout naming the previous → new hash.
- **Run / session correlation.** Each trace row carries `run_id` and
  `session_id`, read from the existing `run_id_ctx` / `session_id_ctx`
  contextvars in `packages._log_context`. Set by the ratchet loop
  (around every `propose_mutation`) and by skill endpoints under
  `/api/v1/hermes/*` that have a run/session in their path
  (`/diagnose-run/{run_id}`, `/analyze-drift/{session_id}`,
  `/explain-anomaly/{run_id}`, `/recommend-quants/{run_id}`,
  `/post-mortem/{run_id}`). The Traces tab shows them as `run #N`
  and `sess #N` chips on each row.
- **Richer filters.** The Traces tab gained: skill multi-select
  (driven by the new activity panel), success / error toggle,
  time range (1h / 24h / 7d / all), min-duration threshold,
  exact run-id, exact session-id. The existing source substring
  and limit selectors are unchanged.
- **`success` materialised column.** New `hermes_traces.success`
  boolean (= `error is None`), indexed; supports cheap
  status filtering without scanning the `error` text column.
- **`binding()` context manager** in `packages._log_context` — a
  thin wrapper around the existing `bind` / `reset` helpers. Use:
  `with binding(run_id=42, session_id=7): ...` and the contextvars
  reset on exit. Replaces the boilerplate `tokens = bind(...);
  try: ...; finally: reset(tokens)` at every call site.

## Changed

- **`load_skill(name)` return type** —
  `str | None` → `tuple[str, str, datetime] | None` (text,
  truncated sha256, filesystem mtime UTC). Internal callers updated.
  External callers in `apps/api/routers/hermes.py` updated.
- **`_call_ollama` / `_record_trace`** now accept optional
  `skill_name` / `skill_sha256` / `skill_mtime` keyword args and
  read `run_id_ctx` / `session_id_ctx` so the persisted trace row
  carries the full correlation set.
- **`GET /api/v1/hermes/traces`** gained query params: `skill[]`
  (repeatable, exact match on `skill_name`), `status`
  (`success` | `error`), `since` / `until` (ISO-8601), `min_duration_ms`,
  `run_id`, `session_id`. Existing `limit`, `source_like`, `tenant_id`
  unchanged.

## Schema migration

Additive only — six new nullable columns appended to `_HERMES_TRACE_MIGRATIONS`
in `apps/api/services/db.py`. Backward-compatible: legacy rows load
with `NULL` for new fields and `success=1` for the materialised flag.

```text
ALTER TABLE hermes_traces ADD COLUMN skill_name   TEXT;
ALTER TABLE hermes_traces ADD COLUMN skill_sha256 TEXT;
ALTER TABLE hermes_traces ADD COLUMN skill_mtime  TIMESTAMP;
ALTER TABLE hermes_traces ADD COLUMN run_id       INTEGER;
ALTER TABLE hermes_traces ADD COLUMN session_id   INTEGER;
ALTER TABLE hermes_traces ADD COLUMN success      INTEGER DEFAULT 1;
```

Indexes: `skill_name`, `run_id`, `session_id`, `success`.

## Auth + redaction

- The new `/api/v1/hermes/traces/skills/summary` endpoint and the
  extended `GET /traces` query parameters inherit the existing
  `@requires("read", "setting")` OPA gate. Admin only.
- Existing PR-1 redaction (`HERMES_TRACE_STORE_PAYLOADS`,
  `HERMES_TRACE_REDACT_SOURCES`) continues to apply to request /
  response bodies. The new fields (`skill_name`, `skill_sha256`,
  `skill_mtime`, `run_id`, `session_id`, `success`) are non-PII and
  are never redacted.

## Migration / rollback

- **Upgrade:** the new columns are added on next `init_db()`; no
  manual step required.
- **Downgrade:** drop the six new columns or restore from backup.
  Existing rows are unaffected — the original column set is
  untouched.

Manual end-to-end (`make dev` + `make trainer` + `make auth ENABLED=false`):

1. Open the UI, sign in, go to **Traces**. Confirm the new filter
   bar (skill multi-select, status, time range, run / session) and
   the left "Skill Activity" panel.
2. Trigger a Hermes call from chat or a ratchet session. The new
   row should carry a `run #N · sess #N` chip when triggered from
   within a session.
3. Edit one of the skill files (`touch .hermes-skills/select_method_for_task.md`
   or change its content), then re-trigger that skill. The new row
   should carry the `✎ skill changed` badge; the detail pane shows
   the new hash + a "changed since previous trace" notice.
