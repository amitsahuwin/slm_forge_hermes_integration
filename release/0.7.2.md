# 0.7.2 — Context-aware persistent chat + chat-auth bug fix

> Format: Keep a Changelog · SemVer 0.7.1 → 0.7.2 — additive features,
> two backward-compatible schema migrations, one user-visible bug fix.

Two things ship together because they're entangled: the existing chat
agent's tool calls were 401-ing under enabled auth (admin user saw
"The API request to access datasets failed due to an authentication
issue") and the underlying chat persistence needed hardening before
that workflow could be trusted day-to-day.

> **Honest framing.** Most of what users asked for — *each chat
> has its own ID, persisted history, context-aware answers* — was
> already in this codebase: `ChatConversation` with auto-increment
> IDs, `ChatMessage` rows linked by `conversation_id`,
> `_load_history_as_langchain` replaying history into the LangGraph
> agent per turn. This release closes the four real gaps the user
> would hit as soon as they used it seriously: tool messages were
> dropped, no token-budget guard, no tenant boundary, no
> observability.

## Fixed

- **Chat auth bug — admin sees "API request to access datasets
  failed due to authentication issue".** The chat agent's LangChain
  tools made raw `httpx` calls back to `localhost:8000` with no
  auth headers. With `SLM_FORGE_AUTH_ENABLED=true` the AuthMiddleware
  401'd every tool call; the `error_remedy` translation surfaced
  the English message in the chat UI.
  Fix: a new `bearer_token_ctx` contextvar in
  `packages._log_context` is bound by `AuthMiddleware` after JWT
  verification and forwarded by every outbound tool call.
  Falls back to `X-Service-Token` in worker contexts where no
  request scope exists. Least-privilege: the agent now acts as the
  user, not a synthetic admin.

## Added

- **Tool / system / summary roles in history replay.**
  `_load_history_as_langchain` now reconstructs the full LangChain
  message sequence — `AIMessage(tool_calls=...)`, `ToolMessage`,
  prepended `SystemMessage` from the latest `role='summary'` row —
  so the agent remembers which tools it already called within a
  conversation.

- **Token-budget guard + in-place summarisation.** New pure module
  `packages/chat_agent/history.py:compose_working_context` keeps
  the last `CHAT_HISTORY_KEEP_LAST_N` turns verbatim (default 8) and
  asks Hermes to summarise the rest when the working context goes
  past `CHAT_HISTORY_MAX_TOKENS` (default 24576 — 75% of qwen3:30b-a3b's
  32k window). The summary is persisted as a `role='summary'` row
  so the next turn re-uses it without another Hermes call.
  Summariser failures (Ollama down) degrade gracefully to a
  wider-verbatim tail.

- **Hermes skill `summarize_chat_window`** — `.hermes-skills/summarize_chat_window.md`.

- **Multi-tenant boundary on chat.** Six new nullable columns:
  - `chat_conversations.tenant_id` (indexed, default `'default'`)
  - `chat_conversations.user_id` (indexed, nullable)
  - `chat_conversations.summary_message_id` (FK-like to latest
    summary row)
  - `chat_conversations.last_summarized_at`
  - `chat_messages.tenant_id` (indexed, denormalised)
  - `chat_messages.token_estimate` (cached `len(content)//4`)

- **Auth gate on every chat endpoint.** `@requires("read", "chat")`
  / `@requires("create", "chat")` — the role matrix already had
  `chat`, just wired through. Plus a row-level ownership check
  (`_load_convo_or_403`): non-admin users can only access
  conversations they own (or ownerless conversations within their
  tenant).

- **`chat:turn` Hermes trace.** Every chat turn writes one
  `hermes_traces` row (source=`chat:turn`, skill_name=`chat:turn`)
  with `conversation_id`, `message_count_in`, `summarization_fired`,
  `tool_result_count`, `duration_ms`. Shows up in the Skill-Activity
  view from 0.7.1 — no new UI.

- **`binding()` context manager** in `packages._log_context` —
  scoped `bind`/`reset` boilerplate eliminator (was added for the
  ratchet loop in 0.7.1; spec'd into chat in 0.7.2).

## Changed

- `_persist_turn` (chat router) now writes discrete `assistant` /
  `tool` rows instead of cramming results into one row's
  `tool_calls_json`. Required for history replay fidelity. Existing
  rows continue to load (the legacy `tool_calls_json` was a list of
  *results*, which `_load_history_as_langchain` now also parses
  for forward compatibility).

## Schema migration

Additive, reversible, idempotent. Six new nullable columns; no data
loss. Run on next `init_db()`.

```text
ALTER TABLE chat_conversations ADD COLUMN tenant_id          TEXT    DEFAULT 'default';
ALTER TABLE chat_conversations ADD COLUMN user_id            TEXT;
ALTER TABLE chat_conversations ADD COLUMN summary_message_id INTEGER;
ALTER TABLE chat_conversations ADD COLUMN last_summarized_at TIMESTAMP;
ALTER TABLE chat_messages      ADD COLUMN tenant_id          TEXT    DEFAULT 'default';
ALTER TABLE chat_messages      ADD COLUMN token_estimate     INTEGER DEFAULT 0;
```

## New env vars

| Name | Default | Effect |
|---|---|---|
| `CHAT_HISTORY_MAX_TOKENS` | `24576` | When the working context exceeds this, summarise the head. |
| `CHAT_HISTORY_KEEP_LAST_N` | `8` | Always keep at least N most-recent turns verbatim. |

Both validated at use site (CLAUDE.md §23: fail-fast on bad config).

Manual end-to-end (`make dev` + `make auth ENABLED=true`):

1. Sign in as admin. Open **Chat** tab.
2. *"my name is Pat"* → *"what's my name?"* → answer should be *"Pat"*.
3. *"list recent runs"* → tool fires successfully (the auth bug is
   fixed). Then *"show metrics for the first one"* — the agent should
   reference the run id from the previous turn's tool result rather
   than re-firing `list_runs`.
4. With `CHAT_HISTORY_MAX_TOKENS=200 CHAT_HISTORY_KEEP_LAST_N=4`,
   send 20 turns. Inspect:
   ```sql
   SELECT role, length(content) FROM chat_messages
   WHERE conversation_id = <id> ORDER BY id;
   ```
   At least one row with `role='summary'` should appear.
5. Open the **Traces** tab → filter by skill `chat:turn`. Each turn
   appears with its message-count + summarization-fired flag.

## Migration / rollback

- **Upgrade:** new columns added on next `init_db()`; no manual step.
- **Downgrade:** drop the six new columns or restore from backup.
  The pre-existing schema is untouched.
